# IntentCI v1 Product Specification

**Status:** Draft  
**Product:** IntentCI  
**Release:** v1.0  
**Primary interface:** Local command-line application  
**Primary implementation language:** Go  
**Tagline:** CI for product intent

---

## 1. Product Summary

IntentCI is a local-first verification system that determines whether a code change satisfies a repository’s approved product requirements.

It runs before code is pushed or a pull request is opened. It combines:

- Persistent product requirements
- Change-specific acceptance criteria
- Git impact analysis
- Repository-native tests and checks
- Architecture and compatibility policies
- Optional semantic analysis
- Requirement-level evidence reporting

IntentCI does not replace unit tests, integration tests, linters, type checkers, or human review. It organizes those tools around product intent and identifies affected requirements that remain unverified.

The primary product output is not a collection of review comments. It is a requirement-to-evidence report:

```text
STATE-001   Failed writes must not advance state       PASS
RETRY-002   Retries must not duplicate records         PASS
API-004     Existing configuration remains compatible  UNVERIFIED
ARCH-003    Core logic remains destination-neutral     FAIL

```

IntentCI is agent-agnostic and language-agnostic. It can evaluate changes created by coding agents or humans and can invoke any repository-native command.

## 2. Problem

Coding agents can increasingly:

1. Interpret a task
2. Modify a repository
3. Write tests
4. Run those tests
5. Decide that the task is complete

This creates a correlated-error problem. The same agent may misunderstand the requirement, implement that misunderstanding, and write tests that confirm it.

Existing development tools answer narrower questions:

- Compilers ask whether code is valid.
- Linters ask whether code follows structural rules.
- Tests ask whether encoded assertions pass.
- Coding agents ask whether they can complete a task.
- PR reviewers identify possible issues in a diff.
- Specification tools help produce plans and requirements.

None provides a standard local gate answering:

> Which approved product requirements are affected by this change, and what evidence demonstrates that each one still holds?

Product intent is usually fragmented across documentation, issues, architecture decisions, tests, historical bugs, and maintainer knowledge. Existing CI executes commands but does not understand why those commands matter or whether an affected product requirement lacks verification.

IntentCI makes product intent persistent, traceable, and verifiable.

## 3. Product Goals

### 3.1 Primary goals

IntentCI v1 must:

1. Represent repository-wide product requirements in a versioned, human-readable contract.
2. Represent change-specific goals, acceptance criteria, and non-goals.
3. Determine which requirements are affected by a Git change.
4. Select and run the relevant repository-native checks locally.
5. identify affected requirements with missing evidence.
6. Produce precise human-readable and machine-readable results.
7. Provide coding agents with actionable feedback before a pull request exists.
8. Cache successful checks safely to keep local iteration fast.
9. Operate without a hosted service.
10. Avoid silently treating inferred requirements as approved product truth.

### 3.2 Secondary goals

IntentCI v1 should:

- Support macOS, Linux, and Windows through WSL.
- Work across programming languages and build systems.
- Integrate with Git pre-push hooks.
- Support optional local or remote semantic-analysis providers.
- Produce an attestation tied to a specific commit and contract version.
- Detect attempts to weaken the product contract within the same change.

---

## 4. Non-Goals

IntentCI v1 will not:

- Benchmark or rank coding agents.
- Execute or supervise coding agents.
- Generate implementation code.
- Replace native test frameworks.
- Replace general-purpose PR review.
- Infer authoritative product requirements without human approval.
- Guarantee correctness in the formal or mathematical sense.
- Provide cryptographic enforcement against a malicious contributor.
- Provide an organization-wide hosted dashboard.
- Perform cross-repository dependency analysis.
- Implement compiler-grade static analysis for every language.
- Automatically merge, push, or open pull requests.
- Require a specific AI model or model provider.
- Upload repository contents by default.
- Replace GitHub Actions or other remote CI where trusted enforcement is required.

---

## 5. Target Users

### 5.1 Primary user: repository maintainer

A maintainer wants coding agents and contributors to produce changes that preserve the repository’s important behaviors, invariants, architecture, and compatibility commitments.

The maintainer defines and approves the Product Contract.

### 5.2 Primary user: coding agent

A coding agent needs a stable, machine-readable definition of completion.

The agent runs IntentCI, receives requirement-level failures, modifies the implementation, and repeats until the change is verified.

### 5.3 Secondary user: contributor

A contributor wants to validate a change locally before consuming remote CI resources or requesting review.

### 5.4 Secondary user: technical lead

A technical lead wants to identify requirements that lack tests, code that violates architecture boundaries, and changes whose product impact is unclear.

---

## 6. Product Principles

### 6.1 Product intent must be explicit

IntentCI may propose requirements, but only requirements marked `approved` are authoritative.

### 6.2 Evidence must be visible

Every status must show why it was assigned and which evidence supports it.

### 6.3 Missing evidence is not success

An affected requirement with no valid verification evidence must never receive `PASS`.

### 6.4 Native tooling remains authoritative

IntentCI orchestrates existing tools rather than replacing them.

### 6.5 Deterministic evidence outranks semantic judgment

A failing deterministic check cannot be overridden by a positive semantic assessment.

### 6.6 Semantic analysis must identify uncertainty

A semantic verifier must be able to return `UNKNOWN` or `UNVERIFIED`. It must not be forced to declare success.

### 6.7 Local execution is the default

All required checks execute on the developer’s machine before the change is pushed.

### 6.8 Contract changes must be conspicuous

An agent must not be able to silently remove a requirement or weaken a check and receive a clean result.

### 6.9 The result format must be agent-compatible

A coding agent must be able to run IntentCI and consume the result without custom integration.

## 7. Core Concepts

IntentCI v1 contains four primary artifacts.

### 7.1 Product Contract

A persistent, version-controlled representation of repository-wide product intent.

It includes:

- Product purpose
- Product non-goals
- Approved requirements
- Requirement applicability
- Verification checks
- Verification policy

Default path:

```text
.intentci/contract.yaml

```

### 7.2 Change Spec

A version-controlled description of the intended change.

It includes:

- Change summary
- Source issue or request
- Goals
- Acceptance criteria
- Non-goals
- Explicitly affected requirements
- Required checks
- Approved waivers

Default path:

```text
.intentci/changes/<change-id>.yaml

```

Acceptance criteria in a Change Spec are treated as temporary requirements for that change.

### 7.3 Verification Result

A generated record describing:

- The evaluated commit
- The evaluated diff
- Affected requirements
- Executed checks
- Evidence
- Findings
- Requirement statuses
- Overall status

Default output directory:

```text
.intentci/results/

```

Generated results should normally be excluded from Git.

### 7.4 Attestation

A compact generated record tying a successful verification run to:

- Commit SHA
- Base commit SHA
- Product Contract hash
- Change Spec hash
- IntentCI version
- Check definitions
- Check results
- Environment fingerprint
- Timestamp

An attestation is useful evidence but is not a trusted security artifact unless signed and validated in trusted infrastructure.

## 8. Requirement Model

A requirement is a stable statement describing behavior or a constraint that the repository must preserve.

### 8.1 Requirement types

IntentCI v1 supports:

- `behavior`
- `invariant`
- `architecture`
- `compatibility`
- `security`
- `reliability`
- `performance`
- `operability`
- `documentation`

### 8.2 Requirement lifecycle

A requirement has one of three lifecycle states:

- `draft`: proposed but not authoritative
- `approved`: authoritative and enforceable
- `deprecated`: retained for history but no longer enforced

Only approved requirements affect the verification result.

### 8.3 Requirement severity

A requirement has one of two severities:

- `blocking`: failure, unknown status, or missing evidence blocks verification
- `advisory`: findings are reported but do not block verification

### 8.4 Stable IDs

Requirement IDs must be unique and stable.

Examples:

```text
STATE-001
API-004
ARCH-003
RETRY-002

```

Changing a requirement statement must not change its ID unless it represents a materially different requirement.

Deleted approved requirements must be marked `deprecated` rather than silently removed.

## 9. Product Contract Format

The Product Contract is YAML and must validate against a versioned JSON Schema distributed with IntentCI.

Example:

```yaml
version: 1

product:
  name: example-pipeline
  purpose: Reliably load source data into supported destinations.
  non_goals:
    - Real-time stream processing
    - Destination-specific transformation logic

policy:
  default_base: origin/main
  unknown_blocks: true
  unverified_blocks: true

  semantic:
    enabled: true
    enforcement: advisory

requirements:
  - id: STATE-001
    type: invariant
    title: Failed writes preserve pipeline state
    statement: Failed destination writes must never advance persisted pipeline state.
    status: approved
    severity: blocking

    sources:
      - path: docs/state-model.md
        description: State persistence contract

    applies_to:
      include:
        - src/state/**
        - src/destinations/**
        - tests/state/**
      exclude:
        - docs/**

    verification:
      mode: all
      checks:
        - state-unit
        - state-failure-integration
      semantic: required

  - id: ARCH-003
    type: architecture
    title: Extraction remains destination-neutral
    statement: Core extraction code must not depend on destination adapters.
    status: approved
    severity: blocking

    applies_to:
      include:
        - src/extract/**
        - src/destinations/**

    verification:
      mode: all
      checks:
        - architecture-boundaries
      semantic: optional

checks:
  - id: state-unit
    description: State-management unit tests
    command: pytest tests/state/unit
    profiles:
      - fast
      - full
    inputs:
      - src/state/**
      - tests/state/unit/**
    timeout: 5m
    cache: success

  - id: state-failure-integration
    description: Destination failure-path integration tests
    command: pytest tests/state/integration/test_destination_failure.py
    profiles:
      - full
    inputs:
      - src/state/**
      - src/destinations/**
      - tests/state/integration/**
    timeout: 15m
    cache: success

    results:
      format: junit
      path: .intentci/tmp/state-failure.xml

  - id: architecture-boundaries
    description: Validate repository architecture boundaries
    command: python scripts/check_architecture.py
    profiles:
      - fast
      - full
    inputs:
      - src/**
      - scripts/check_architecture.py
    timeout: 2m
    cache: success

```

## 10. Change Spec Format

A Change Spec defines the product intent of the current change.

Example:

```yaml
version: 1

id: RETRY-123
status: approved
type: feature

summary: Add retry support for transient destination failures.

source:
  type: github_issue
  reference: "#123"

goals:
  - Retry transient destination failures without losing progress.
  - Preserve existing incremental-loading behavior.

non_goals:
  - Retrying permanent authentication failures
  - Changing the public connector configuration format
  - Adding asynchronous execution

acceptance:
  - id: AC-001
    statement: A transient destination failure is retried up to the configured limit.
    severity: blocking
    verification:
      checks:
        - retry-integration
      semantic: required

  - id: AC-002
    statement: Failed attempts do not advance persisted pipeline state.
    severity: blocking
    verification:
      checks:
        - state-failure-integration
      semantic: required

affected_requirements:
  - STATE-001
  - API-004
  - RETRY-002

required_checks:
  - retry-integration

waivers: []

```

### 10.1 Change Spec requirements

A Change Spec must:

- Have a unique ID.
- Have a concise summary.
- State at least one goal.
- State explicit non-goals when scope ambiguity is likely.
- Define acceptance criteria for new user-visible behavior.
- Reference affected persistent requirements when known.

### 10.2 Change Spec approval

IntentCI v1 assumes approved Change Specs are reviewed through the repository’s normal process.

IntentCI detects modifications to approved Change Specs but does not cryptographically establish who approved them.

## 11. Verification Status Model

Each affected requirement receives one status.

### 11.1 `PASS`

A requirement receives `PASS` only when:

- All required checks selected by its verification policy pass.
- Required evidence exists.
- No deterministic contradiction exists.
- No blocking semantic finding remains unresolved.
- The requirement has not been improperly weakened in the current change.

### 11.2 `FAIL`

A requirement receives `FAIL` when:

- A required check exits unsuccessfully.
- A required test fails.
- A deterministic policy identifies a violation.
- A required artifact is incompatible or invalid.
- Semantic enforcement is configured as blocking and produces a qualifying contradiction.

### 11.3 `UNVERIFIED`

A requirement receives `UNVERIFIED` when:

- The requirement is affected but has no required checks.
- A required evidence file is missing.
- Existing checks do not cover the affected path or behavior.
- Semantic analysis identifies a plausible requirement impact with insufficient evidence.
- A Change Spec acceptance criterion lacks a verification mechanism.

### 11.4 `UNKNOWN`

A requirement receives `UNKNOWN` when:

- A required tool is unavailable.
- A check times out.
- Git state cannot be resolved.
- A check crashes without a meaningful result.
- Semantic analysis is required but unavailable.
- IntentCI cannot determine whether the requirement still holds.

### 11.5 `WAIVED`

A requirement receives `WAIVED` when:

- A valid, explicit waiver exists.
- The waiver identifies the requirement.
- The waiver includes a reason.
- The waiver includes an owner or approver.
- The waiver has not expired.

Waived blocking requirements do not block the run, but every waiver must appear prominently in the report.

### 11.6 `NOT_AFFECTED`

A requirement receives `NOT_AFFECTED` when the impact engine finds no applicable code, configuration, contract, or acceptance-criterion changes.

This status is included in full reports but omitted from concise terminal output.

---

## 12. Overall Run Status

The overall run status follows this precedence:

```text
FAIL
UNKNOWN
UNVERIFIED
PASS

```

A run is `PASS` only when every affected blocking requirement is either:

- `PASS`, or
- validly `WAIVED`

Advisory requirements never determine the overall result.

---

## 13. Impact Analysis

The impact engine determines which requirements and checks are relevant to a change.

### 13.1 Inputs

The impact engine uses:

- Base commit
- Head commit or working tree
- Changed files
- Added and removed files
- Product Contract changes
- Change Spec
- Requirement `applies_to` rules
- Check input rules
- Explicit affected-requirement declarations
- Optional semantic analysis

### 13.2 Impact resolution order

Requirements become affected through the following mechanisms:

1. Explicit declaration in the Change Spec
2. Matching `applies_to.include` paths
3. Matching a mapped check’s input paths
4. Changes to a requirement’s source documentation
5. Changes to the requirement or its check definition
6. Optional semantic impact detection

Explicit exclusions may suppress path-based impact but may not override explicit declarations.

### 13.3 Conservative behavior

When IntentCI cannot safely determine that a blocking requirement is unaffected, it should prefer `UNKNOWN` or `UNVERIFIED` over `NOT_AFFECTED`.

### 13.4 v1 analysis granularity

IntentCI v1 provides file-level and check-level impact analysis.

Symbol-level and semantic dependency-graph analysis are deferred beyond v1.

This means v1 may occasionally run more checks than strictly necessary, but it must not silently omit a clearly mapped check.

## 14. Contract-Change Protection

Agents and contributors may modify `.intentci/contract.yaml`. IntentCI must detect attempts to weaken the verification policy.

### 14.1 Base Contract

IntentCI loads:

- The Product Contract from the base commit
- The Product Contract from the working tree or head commit

### 14.2 Protected changes

IntentCI must flag:

- Removal of an approved requirement
- Changing an approved requirement to `draft`
- Lowering severity from `blocking` to `advisory`
- Removing a required check
- Changing verification mode from `all` to `any`
- Disabling required semantic analysis
- Narrowing requirement applicability
- Changing or deleting a blocking check
- Adding a waiver

### 14.3 Effective policy

For ordinary code changes, the effective verification policy must not be weaker than the base contract.

A removed or weakened base requirement remains active for the current verification run.

New or strengthened requirements from the head contract also apply.

### 14.4 Contract updates

A legitimate contract update must use a Change Spec with:

```yaml
type: contract

```

IntentCI still reports every weakened or removed rule and returns `UNVERIFIED` unless the change contains an explicit waiver or approval mechanism accepted by repository policy.

IntentCI v1 detects contract weakening but does not provide cryptographic maintainer approval.

## 15. Check Execution

### 15.1 Execution model

IntentCI executes repository-defined commands as subprocesses on the local host.

Examples:

```text
pytest
go test ./...
cargo test
npm test
mvn verify
dbt build
python scripts/check_api_compatibility.py

```

### 15.2 v1 runner support

IntentCI v1 supports:

- Local host subprocesses

Deferred:

- Native OCI container execution
- Remote runners
- Distributed execution
- Hosted execution

Repositories may invoke containers through their own check commands.

### 15.3 Check dependency graph

Checks may define dependencies:

```yaml
checks:
  - id: integration
    command: pytest tests/integration
    depends_on:
      - unit

```

A dependent check must not run when a prerequisite fails unless explicitly configured.

### 15.4 Parallel execution

Independent checks should run concurrently.

The default concurrency limit should be based on available CPUs and configurable through:

```yaml
execution:
  max_parallel: 4

```

Checks may declare:

```yaml
exclusive: true

```

An exclusive check runs without other checks executing concurrently.

### 15.5 Timeouts

Every check must have a timeout.

A timeout produces `UNKNOWN` unless repository policy explicitly treats timeouts as failures.

### 15.6 Environment

Checks inherit a minimal environment.

Configuration may explicitly include environment variables in the cache key:

```yaml
environment:
  include:
    - PYTHON_VERSION
    - DATABASE_URL

```

Secret values must not be written into reports or attestations.

---

## 16. Check Profiles

IntentCI provides two standard profiles.

### 16.1 Fast profile

Used by:

```bash
intentci check

```

The fast profile is intended for repeated development-loop execution.

It typically includes:

- Affected unit tests
- Linters
- Type checks
- Architecture checks
- Schema validation
- Fast semantic analysis

### 16.2 Full profile

Used by:

```bash
intentci verify

```

The full profile is intended before pushing.

It includes:

- All required affected checks
- Integration tests
- Compatibility checks
- Required semantic analysis
- Documentation checks
- Attestation generation when requested

A blocking requirement must not receive `PASS` from the fast profile when its full-profile evidence has not been executed. The fast command may instead report:

```text
PROVISIONAL PASS

```

Provisional results do not produce a successful attestation.

---

## 17. Caching

### 17.1 Objective

Repeated verification should avoid rerunning successful checks whose relevant inputs have not changed.

### 17.2 Cache key

The cache key must include:

- IntentCI version
- Check definition
- Command
- Relevant input content hashes
- Product Contract hash
- Change Spec hash where applicable
- Declared environment values
- Operating system and architecture
- Toolchain fingerprint when declared
- Dependency lockfile hashes

### 17.3 Cache policy

Supported values:

- `off`
- `success`

IntentCI v1 caches successful checks only.

Failures, timeouts, and unknown results are not reused.

### 17.4 Cache safety

A check without declared inputs must not be cached by default.

A repository may declare broad inputs:

```yaml
inputs:
  - "**"

```

### 17.5 Cache location

Default:

```text
~/.cache/intentci/

```

The cache must be content-addressed and safe to delete at any time.

Corrupt cache entries must be discarded automatically without failing the verification run.

## 18. Semantic Verification

Semantic verification is optional but is a core v1 capability.

Its purpose is to detect product-level contradictions or missing evidence that native checks do not encode.

### 18.1 Semantic inputs

The semantic verifier may receive:

- Approved requirement statements
- Change Spec goals and non-goals
- Git diff
- Relevant source files
- Relevant tests
- Requirement source documents
- Deterministic check results
- Existing evidence mappings

### 18.2 Semantic outputs

The provider must return structured findings:

```json
{
  "requirement_id": "STATE-001",
  "assessment": "contradiction",
  "confidence": 0.94,
  "summary": "State is persisted before destination acknowledgement.",
  "evidence": [
    {
      "path": "src/state/commit.py",
      "line_start": 84,
      "line_end": 91
    }
  ],
  "missing_evidence": [
    "A test that fails the destination write and checks persisted cursor state"
  ]
}

```

Allowed assessments:

- `aligned`
- `contradiction`
- `insufficient_evidence`
- `uncertain`
- `not_affected`

### 18.3 Enforcement

Supported modes:

- `off`
- `advisory`
- `blocking`

Default:

```yaml
semantic:
  enforcement: advisory

```

In advisory mode, semantic analysis may change an otherwise passing requirement to `UNVERIFIED`, but it may not override a deterministic pass with `FAIL`.

In blocking mode, a semantic contradiction may produce `FAIL` when:

- Confidence meets the configured threshold.
- The finding cites concrete repository evidence.
- The requirement is approved.
- The requirement explicitly requires semantic verification.

### 18.4 Provider interface

IntentCI must be model-provider-neutral.

v1 supports a versioned JSON request/response protocol through:

- A local executable
- A configurable HTTP JSON endpoint

The core CLI must not require a model provider.

### 18.5 Privacy

No repository content is sent over a network unless the user explicitly configures a remote semantic provider.

IntentCI must provide:

```bash
intentci verify --show-semantic-input

```

This displays which files and snippets would be sent before any remote request occurs.

### 18.6 Authority

Semantic analysis may:

- Map changes to approved requirements
- Identify contradictions
- Identify missing tests
- Propose draft requirements
- Explain uncertainty

Semantic analysis may not:

- Approve a requirement
- Remove a requirement
- Create a waiver
- Silently change verification policy
- Override deterministic failures

## 19. CLI Specification

The executable is:

```text
intentci

```

### 19.1 Initialize

```bash
intentci init

```

Creates:

```text
.intentci/
├── contract.yaml
├── changes/
└── .gitignore

```

Initialization may detect common test commands and propose draft checks.

Any generated requirements must be marked `draft`.

### 19.2 Validate configuration

```bash
intentci validate

```

Validates:

- Product Contract schema
- Change Spec schemas
- Duplicate IDs
- Missing check references
- Dependency cycles
- Invalid globs
- Invalid waiver dates
- Invalid verification policies

### 19.3 Create a Change Spec

```bash
intentci change create RETRY-123

```

Creates:

```text
.intentci/changes/RETRY-123.yaml

```

### 19.4 Run fast verification

```bash
intentci check

```

Optional flags:

```text
--base <ref>
--change <id>
--all
--no-cache
--format text|json
--output <path>

```

### 19.5 Run full verification

```bash
intentci verify

```

Optional flags:

```text
--base <ref>
--change <id>
--all
--no-cache
--format text|json
--output <path>
--attest
--show-semantic-input

```

### 19.6 Explain a requirement

```bash
intentci explain STATE-001

```

Displays:

- Requirement statement
- Requirement sources
- Applicability rules
- Mapped checks
- Current evidence
- Recent local result
- Relevant changed files
- Semantic findings

### 19.7 Install Git hook

```bash
intentci hook install

```

Installs a pre-push hook that runs:

```bash
intentci verify --attest

```

The existing hook must be preserved or composed rather than overwritten without confirmation.

### 19.8 Remove Git hook

```bash
intentci hook uninstall

```

Removes only the IntentCI-managed hook section.

## 20. Exit Codes

IntentCI uses stable exit codes:


| Code | Meaning                                          |
| ---- | ------------------------------------------------ |
| `0`  | Verification passed                              |
| `10` | One or more blocking requirements failed         |
| `11` | One or more blocking requirements are unverified |
| `12` | One or more blocking requirements are unknown    |
| `20` | Invalid Product Contract or Change Spec          |
| `21` | Missing prerequisite, tool, or base reference    |
| `30` | IntentCI internal error                          |


Agents should use the structured result rather than parsing terminal text.

## 21. Human-Readable Output

Default terminal output must be concise and evidence-focused.

Example:

```text
IntentCI verification failed

Base:   21ad9c1
Head:   76eaa42
Change: RETRY-123

Requirements
  PASS        RETRY-002  Retries do not duplicate records
  FAIL        STATE-001  Failed writes preserve pipeline state
  UNVERIFIED  API-004    Existing configuration remains compatible

STATE-001 — FAIL
  Check: state-failure-integration
  Failure: test_cursor_not_advanced_on_write_failure

  Evidence:
    src/state/commit.py:84-91
    tests/state/test_failure.py:42-68

  Required action:
    Persist state only after destination acknowledgement.

API-004 — UNVERIFIED
  Changed:
    src/config/retry.py

  Missing evidence:
    No compatibility check covers existing retry configuration.

Summary
  1 passed
  1 failed
  1 unverified
  4 checks executed
  3 checks restored from cache

```

Output must avoid generic comments such as:

```text
Consider improving error handling.

```

Findings must identify:

- The affected requirement
- The relevant evidence
- Why the evidence is insufficient or contradictory
- The concrete completion condition

## 23. Attestation Format

An attestation contains:

```json
{
  "schema_version": 1,
  "intentci_version": "1.x",
  "status": "pass",
  "base_commit": "21ad9c1",
  "head_commit": "76eaa42",
  "contract_hash": "sha256:...",
  "change_spec_hash": "sha256:...",
  "check_definition_hash": "sha256:...",
  "environment_hash": "sha256:...",
  "completed_at": "2026-07-25T12:00:00Z",
  "checks": [
    {
      "id": "state-unit",
      "status": "pass",
      "result_hash": "sha256:..."
    }
  ]
}

```

Attestations must never include:

- Secret environment-variable values
- Full command output
- Source-code contents
- Model prompts
- Credentials

A changed commit invalidates the attestation.

---

## 24. Git Integration

### 24.1 Default base

The default comparison base is:

```yaml
policy:
  default_base: origin/main

```

IntentCI compares against the Git merge base rather than assuming the remote branch head is a direct ancestor.

### 24.2 Working tree support

IntentCI must support verification of:

- Committed changes
- Staged changes
- Unstaged changes
- Newly created files

The result must clearly state whether the working tree was dirty.

### 24.3 Pre-push hook

The pre-push hook blocks the push when `intentci verify` exits non-zero.

IntentCI must clearly document that Git hooks can be bypassed using Git options and therefore do not provide trusted organizational enforcement.

## 25. Security and Trust Model

### 25.1 Repository trust

IntentCI executes repository-defined commands. Running IntentCI on an untrusted repository is equivalent to running that repository’s build or test scripts.

IntentCI must display a warning before executing commands from a repository that has not previously been trusted locally.

### 25.2 Network behavior

IntentCI must perform no network requests by default except those initiated by repository-defined checks.

IntentCI-owned network requests require explicit configuration.

### 25.3 Secrets

IntentCI must:

- Redact values matching configured secret environment variables.
- Avoid persisting complete process environments.
- Avoid storing model credentials in repository configuration.
- Use operating-system credential storage or environment variables for provider credentials.

### 25.4 Agent threat model

IntentCI v1 assumes agents may make incorrect changes but are not actively attempting to compromise the verifier.

IntentCI detects contract weakening and check modification, but trusted enforcement against a malicious agent requires:

- Protected branches
- Code ownership
- Signed attestations
- Trusted CI validation

Those controls are outside v1.

### 25.5 Command isolation

IntentCI v1 does not sandbox check commands.

Containerized and sandboxed runners are deferred.

---

## 26. Reliability Requirements

IntentCI must:

- Never report `PASS` when a required check did not run.
- Never report `PASS` when required evidence is missing.
- Never reuse a cached result when a declared input changed.
- Recover safely from a corrupt local cache.
- Cancel dependent checks when prerequisites fail.
- Handle interrupted runs without corrupting future results.
- Produce deterministic results when semantic analysis is disabled.
- Preserve complete machine-readable results even when terminal output is truncated.
- Validate all configuration before executing commands.
- Detect cycles in check dependencies.
- Detect duplicate requirement and check IDs.

---

## 27. Performance Requirements

Performance measurements exclude the runtime of repository-defined checks.

Targets for a warm local repository:

- CLI startup: under 300 ms
- Git diff and file-level impact analysis: under 2 seconds for 100,000 tracked files and 1,000 changed files
- Cached-check resolution: under 100 ms per check
- Scheduler overhead: less than 5% of total executed-check runtime
- Memory usage: under 300 MB for typical repositories
- JSON report generation: under 500 ms

A repository check must begin streaming output immediately after execution starts.

## 28. User Experience Requirements

### 28.1 Onboarding

A repository with an existing test suite should be able to install IntentCI and configure its first blocking requirement in under 30 minutes.

### 28.2 Error messages

Errors must explain:

- What failed
- Why it matters
- Which file or configuration caused it
- How to resolve it

### 28.3 Progressive adoption

IntentCI must support adoption in stages:

1. Define one blocking invariant.
2. Map it to an existing test.
3. Run local verification.
4. Add Change Specs.
5. Add semantic analysis.
6. Add more architecture and compatibility requirements.

Repositories must not need to formalize every product requirement before obtaining value.

### 28.4 No noisy success output

Successful runs should default to a compact summary.

Detailed evidence should be available through:

```bash
intentci explain <requirement-id>

```

## 29. Primary User Workflows

### 29.1 Agent implements a feature

```text
1. Maintainer or agent creates a Change Spec.
2. Maintainer approves the product intent.
3. Agent modifies code and tests.
4. Agent runs `intentci check`.
5. IntentCI returns affected requirement results.
6. Agent fixes failures or missing evidence.
7. Agent runs `intentci verify --attest`.
8. Verification passes.
9. Agent pushes the branch and opens a PR.

```

### 29.2 Agent fixes a bug

```text
1. Change Spec records the observed failure and expected behavior.
2. Acceptance criteria require a regression test.
3. Agent implements the fix.
4. IntentCI verifies the regression test and persistent invariants.
5. The change cannot pass solely because the original test suite passes.

```

### 29.3 Refactor without behavior change

```text
1. Change Spec declares behavior preservation as the goal.
2. Persistent behavior and architecture requirements are selected.
3. IntentCI runs affected tests and compatibility checks.
4. New user-facing behavior is flagged as outside the declared scope.

```

### 29.4 Contract update

```text
1. Change Spec type is `contract`.
2. IntentCI compares base and head contracts.
3. Every weakened, removed, or newly added requirement is reported.
4. Base requirements remain active for the current run.
5. Human review decides whether the contract change is legitimate.

```

## 30. v1 Functional Requirements

### Contract management

- **IC-CONTRACT-001:** IntentCI must load and validate a versioned Product Contract.
- **IC-CONTRACT-002:** IntentCI must reject duplicate requirement IDs.
- **IC-CONTRACT-003:** IntentCI must enforce only approved requirements.
- **IC-CONTRACT-004:** IntentCI must retain and report deprecated requirements.
- **IC-CONTRACT-005:** IntentCI must detect contract weakening relative to the base commit.

### Change specifications

- **IC-CHANGE-001:** IntentCI must load a Change Spec by explicit ID.
- **IC-CHANGE-002:** IntentCI must convert acceptance criteria into temporary requirements.
- **IC-CHANGE-003:** IntentCI must include explicit affected requirements in impact analysis.
- **IC-CHANGE-004:** IntentCI must report modifications to an approved Change Spec.

### Impact analysis

- **IC-IMPACT-001:** IntentCI must identify changed files using Git.
- **IC-IMPACT-002:** IntentCI must map changed files to requirements through path rules.
- **IC-IMPACT-003:** IntentCI must map changed files to checks through declared inputs.
- **IC-IMPACT-004:** IntentCI must conservatively report uncertain impact.
- **IC-IMPACT-005:** IntentCI must support explicit full verification.

### Check execution

- **IC-RUN-001:** IntentCI must execute arbitrary local commands.
- **IC-RUN-002:** IntentCI must support check dependencies.
- **IC-RUN-003:** IntentCI must run independent checks concurrently.
- **IC-RUN-004:** IntentCI must enforce check timeouts.
- **IC-RUN-005:** IntentCI must stream subprocess output.
- **IC-RUN-006:** IntentCI must preserve stdout and stderr in the result record.
- **IC-RUN-007:** IntentCI must support optional JUnit result parsing.

### Evidence and status

- **IC-EVIDENCE-001:** Every affected requirement must receive a status.
- **IC-EVIDENCE-002:** Every non-pass status must include a reason.
- **IC-EVIDENCE-003:** PASS must require all mandatory evidence.
- **IC-EVIDENCE-004:** Missing evidence must produce UNVERIFIED.
- **IC-EVIDENCE-005:** Tool or execution uncertainty must produce UNKNOWN.
- **IC-EVIDENCE-006:** Deterministic failures must outrank semantic assessments.

### Caching

- **IC-CACHE-001:** IntentCI must cache successful checks by content.
- **IC-CACHE-002:** Cache keys must include declared inputs and check definitions.
- **IC-CACHE-003:** Checks without inputs must not be cached by default.
- **IC-CACHE-004:** Cache corruption must not fail verification.

### Semantic verification

- **IC-SEMANTIC-001:** Semantic verification must be optional.
- **IC-SEMANTIC-002:** Semantic results must use a structured schema.
- **IC-SEMANTIC-003:** Semantic findings must cite repository evidence.
- **IC-SEMANTIC-004:** Semantic providers must not alter Product Contracts.
- **IC-SEMANTIC-005:** Remote semantic analysis must require explicit configuration.

### Agent integration

- **IC-AGENT-001:** IntentCI must provide stable JSON output.
- **IC-AGENT-002:** IntentCI must use stable exit codes.
- **IC-AGENT-003:** Findings must identify concrete completion conditions.
- **IC-AGENT-004:** IntentCI must not require agent-specific adapters.

### Git integration

- **IC-GIT-001:** IntentCI must compare against the Git merge base.
- **IC-GIT-002:** IntentCI must support dirty working trees.
- **IC-GIT-003:** IntentCI must install and uninstall a managed pre-push hook.
- **IC-GIT-004:** IntentCI must never silently overwrite an existing hook.

## 31. v1 Release Acceptance Criteria

IntentCI v1 is complete when all of the following are true.

### Repository support

IntentCI successfully verifies fixture repositories using:

- Python
- Go
- TypeScript or JavaScript
- Rust

The implementation must not contain language-specific execution logic for those repositories beyond fixture configuration.

### Product Contract

- A user can define blocking requirements.
- Requirements can map to checks and paths.
- Invalid contracts fail before command execution.
- Contract weakening is detected against the base commit.

### Change Spec

- A user can create and select a Change Spec.
- Acceptance criteria appear as requirement-level results.
- Explicit goals and non-goals are included in semantic input.
- Missing verification for an acceptance criterion produces `UNVERIFIED`.

### Verification

- A changed file selects the correct requirements.
- Required checks execute in dependency order.
- Independent checks execute concurrently.
- Failing checks produce `FAIL`.
- Missing checks produce `UNVERIFIED`.
- Timeouts produce `UNKNOWN`.
- All passing evidence produces `PASS`.

### Cache

- An unchanged successful check is restored from cache.
- Modifying any declared input invalidates the cache.
- Modifying the check command invalidates the cache.
- Modifying the Product Contract invalidates relevant entries.

### Output

- Text output is understandable without reading logs.
- JSON output validates against the published schema.
- Every failure identifies a requirement.
- Every failure includes actionable evidence.
- An agent can determine the next action using JSON alone.

### Local workflow

- `intentci check` supports a fast development loop.
- `intentci verify` performs full local verification.
- The pre-push hook blocks a push on non-zero status.
- A passing verification can generate an attestation.

### Privacy

- IntentCI makes no network requests by default.
- No remote semantic request occurs without explicit configuration.
- Reports and attestations do not expose configured secrets.

## 32. Implementation Architecture

The Go application should use the following internal modules:

```text
cmd/intentci
internal/
├── cache
├── config
├── contract
├── changespec
├── evidence
├── git
├── impact
├── report
├── runner
├── scheduler
├── semantic
├── attest

pkg/
├── protocol
└── schema

```

### 32.1 System flow

```text
Load configuration
        ↓
Validate schemas and references
        ↓
Resolve base and head Git state
        ↓
Load base and head Product Contracts
        ↓
Load selected Change Spec
        ↓
Determine changed files
        ↓
Resolve affected requirements
        ↓
Construct check dependency graph
        ↓
Restore valid cached results
        ↓
Execute remaining checks
        ↓
Parse deterministic evidence
        ↓
Run optional semantic verification
        ↓
Assign requirement statuses
        ↓
Generate text and JSON reports
        ↓
Generate optional attestation
        ↓
Return stable exit code

```

### 32.2 Storage

IntentCI should use:

- YAML for human-authored configuration
- JSON for generated results and protocols
- SQLite or an embedded key-value store for cache metadata
- Content-addressed files for cached outputs

### 32.3 Git implementation

IntentCI should use the installed Git executable for:

- Merge-base calculation
- Diff generation
- Object hashes
- Worktree status
- Reading files from the base commit

This avoids subtle divergence from Git’s actual behavior.

## 35. Product Positioning

IntentCI should be positioned as:

> A local verification layer that checks code changes against persistent product intent before they reach a pull request.

It should not be positioned as:

- An AI code reviewer
- A test framework
- An agent runtime
- A specification generator
- A formal verification system
- A replacement for CI

The category statement is:

> **IntentCI is CI for product intent.**

The core distinction is:

```text
Traditional CI
  command → exit code

IntentCI
  product requirement
      → affected implementation
          → required checks
              → evidence
                  → requirement status

```

## 36. Definition of v1 Success

IntentCI v1 succeeds when a maintainer can take an existing repository, define several important product invariants, map them to existing checks, and give any coding agent a single command that reliably answers:

1. What product requirements did this change affect?
2. Which requirements are proven to hold?
3. Which requirements failed?
4. Which requirements remain unverified?
5. What exact evidence or implementation change is needed before the work is complete?

The defining v1 behavior is:

```text
agent edits
    → intentci check
        → structured requirement failures
            → agent repairs
                → intentci verify
                    → local evidence-backed pass
                        → push

```
